# Backend source and readiness

This is reviewable source, not a deployed or accepted service. The owner has left free capacity pending. Do not provision, deploy these ownership policies, set environment values, run backend checks, or run cleanup without the corresponding explicit approval. No login retry, service mutation, upload, deletion, model call or live backend check was performed while authoring this source.

## Boundary and configuration

Next's server-only adapter calls two relay-authenticated HTTP actions; every database function is internal. Generic official Convex builders avoid checking generated files into this source. No admin authentication API or public database mutation is used. Owner and preview capabilities are separate canonical 32-byte base64url values; only domain-separated SHA-256 hashes are persisted. Capabilities are not recoverable from the service. An author must preserve their private ownership backup.

After readiness approval, Next requires `LINEN_PUBLISHING_ENABLED=true`, `LINEN_CONVEX_SITE_URL` (the isolated deployment's HTTPS `.convex.site` origin), `LINEN_RELAY_SECRET` (a canonical random 32-byte base64url value), and `LINEN_SITE_URL` (the official app origin). Convex requires the same relay secret and its own explicit `LINEN_PUBLISHING_ENABLED=true`. Defaults fail closed. Syntactically valid configuration is not runtime, eligibility or capacity proof. No configuration was applied here.

Claims reserve handle/page ID atomically. Same page ID and owner capability return the existing profile; a different owner cannot claim it. Draft saves compare revisions, and publication copies the exact validated draft and completed references into a separate published revision. Handles/page IDs remain immutable. Preview rotation/revocation does not change publication. Confirmed deletion first marks a profile inaccessible, then deletes its bounded media and content atomically; failed cleanup leaves the owner able to retry deletion. A minimal page-ID/owner-hash tombstone prevents a late claim from resurrecting deleted content, and the old handle is released.

## Media

Reservation is `POST /api/profiles/[handle]/media` with `{id,name,type,size,sha256}`. The lowercase 64-character SHA-256 must come from the actual local Blob. A completed matching ID/hash returns `{uploaded:true}`; different bytes/type/size under the same ID return `409 asset_id_conflict`. Otherwise `{uploadUrl}` permits a direct upload to the validated corresponding `.convex.cloud` upload origin. Finalize with `PUT {id,storageId}`; success returns the current `OwnerSnapshot`. The upload receipt's storage ID is private transient uploader input, never a public manifest field.

Finalization atomically binds a fresh, previously unclaimed storage ID to the owned reservation, checks actual `_storage` metadata, reads the real Blob, validates its signature with the canonical media helper, and independently hashes its bytes. Only then can it become referenced published media; publication checks image/video MIME compatibility too. Repeating reservation after a lost finalization response resumes an already bound verification instead of requiring another upload. Node-runtime internal finalization has the documented 512 MiB memory budget, avoiding 32 MiB video hashing inside the 64 MiB HTTP runtime. These are source choices, not proven provider resource usage.

The documented direct-upload API does not stamp our reservation ID onto a receipt. A fresh unclaimed receipt plus expected content hash establishes integrity; it does not independently prove which upload URL produced that receipt. Raw receipts must remain private. A receipt already bound to another reservation cannot be reassigned or deleted. Failed validation removes only the proven caller-owned binding's Blob, retaining the reservation for retry. No arbitrary supplied storage ID is deleted.

Public manifests expose client UUIDs and access-checked proxy paths only. Owner reads can retrieve that profile's ready assets; previews can retrieve current-draft references; anonymous reads can retrieve current-published references. The proxy rechecks access after storage I/O and uses no-store/referrer protections. Range responses support video without issuing durable storage URLs. Revocation affects future service reads; it cannot undo completed downloads or an already authorized in-flight response. Owner editors must fetch private assets with their bearer then display local Blob URLs. Preview paths carry only the separate read-only token.

## Source quotas and cleanup

Application hard caps: 100 lifetime profile claims (including minimal deletion tombstones), 64 media reservations per profile, contract limits of 8 MiB/image, 32 MiB/video and 64 MiB/profile, 256 MiB total reserved/ready media, and 1,024 lifetime upload-URL issuances. Deletion releases reserved bytes; lifetime counters are not silently reset. These are bounded source safeguards, not measured remaining free allowances or general abuse protection. Direct-upload URLs cannot enforce our MIME/size/signature rules before the provider receives bytes. Abandoned or oversized uploads may temporarily consume provider capacity. Verify isolated-project capacity, hard free-tier limits, operational alerts and abuse handling before readiness approval.

Owners may remove unreferenced reservations/assets through the media DELETE API. Pending draft references should be removed first. If an upload finishes after profile deletion, its receipt is lost, or finalization never reaches binding, an unbound provider object can remain. There is no automatic cleanup or cron. On the isolated Linen deployment only, an explicitly authorized operator can page `maintenance:orphans` (50 objects per cursor), review the exact unbound objects older than 48 hours, then invoke `maintenance:purgeOrphans` with an approved list of at most 25 IDs and `confirm:true`. The mutation rechecks age and lack of a current binding before deleting. Never repurpose this for a shared project's other files, and never delete the entire storage table. Expired reservations still bound to media are deliberately excluded; use owned unreferenced deletion or separately reviewed operator repair.
